EcoPixel

EcoPixel

O EcoPixel converte imagens para WebP no dispositivo do visitante e informa quanto de CO₂ foi evitado por enviar um arquivo menor.

Ele é escrito em Rust e compilado para WebAssembly, então um site pode chamá-lo a partir de JavaScript. Também pode ser usado como uma crate Rust comum.

Por que converter no navegador?

Normalmente o navegador envia o PNG ou JPEG original e o servidor o converte, isso quando alguém converte. Se o navegador converter a imagem antes, um arquivo menor trafega pela rede e o servidor tem menos trabalho. A quantidade de dados que não precisou trafegar é a base do valor de CO₂.

O valor é uma estimativa, não uma medição. Veja A estimativa de CO₂ para saber exatamente o que ela leva em conta.

O que ele faz

  • Lê arquivos PNG, JPEG, GIF, BMP, TIFF e WebP, recebidos como bytes ou como data URL.
  • Converte para WebP: sem perdas, com perdas ou escolhido automaticamente.
  • Transforma GIFs animados em WebP animado.
  • Informa o tamanho original, o novo tamanho, os bytes economizados e o CO₂ economizado estimado.
  • Roda inteiramente no dispositivo do visitante. A biblioteca não envia nada.

O fluxo em quatro passos

  1. Envolva o arquivo com ImageInput. Isso detecta o formato.
  2. Opcionalmente, faça uma prévia da conversão. Ela dá uma estimativa rápida de tamanho sem codificar nada.
  3. Converta a imagem. Você recebe os bytes do WebP e as estatísticas.
  4. Use o resultado. Envie o WebP ou, se ele não ficou menor, o arquivo original.

Continue em Compilando o pacote ou vá direto ao Início rápido se você já tem o pacote compilado.

Compilando o pacote

O EcoPixel é compilado para WebAssembly com o wasm-pack, que também gera o wrapper JavaScript e as definições de tipos do TypeScript.

Pré-requisitos

Você precisa de uma toolchain do Rust, do alvo WebAssembly e do wasm-pack:

rustup target add wasm32-unknown-unknown
cargo install wasm-pack

Compilar

Execute isto na pasta da crate:

wasm-pack build --target web --release

O resultado é uma pasta pkg/ contendo:

ArquivoO que é
eco_pixel_bg.wasmA biblioteca compilada
eco_pixel.jsCódigo JavaScript de ligação; é o que você importa
eco_pixel.d.tsTipos do TypeScript, incluindo os comentários de documentação
package.jsonMetadados do pacote, para que a pasta possa ser publicada ou instalada

Recompile a cada alteração no código Rust e force a atualização da página (Ctrl+F5) para que o navegador não use uma cópia em cache.

Servindo os arquivos

Os navegadores se recusam a carregar WebAssembly de uma página aberta com file://. Sirva a pasta por HTTP com qualquer servidor de arquivos estáticos. Por exemplo:

python -m http.server 8080

Depois abra http://localhost:8080/. O servidor precisa enviar os arquivos .wasm com o tipo de conteúdo application/wasm. A maioria dos servidores estáticos faz isso, e é a primeira coisa a verificar se o módulo não carregar.

Início rápido (JavaScript)

Esta página é um exemplo completo: escolha uma imagem, converta para WebP e mostre quanto foi economizado. Ela pressupõe que você já compilou o pacote (veja Compilando o pacote) e que a pasta pkg/ está ao lado do seu arquivo HTML.

<input id="file" type="file" accept="image/*">
<p id="result"></p>

<script type="module">
  import init, { ImageInput, convert_image_to_webp_auto } from "./pkg/eco_pixel.js";

  await init(); // carrega o módulo WebAssembly uma única vez

  document.getElementById("file").addEventListener("change", async (event) => {
    const file = event.target.files[0];
    if (!file) return;

    try {
      // 1. Envolva os bytes do arquivo.
      const bytes = new Uint8Array(await file.arrayBuffer());
      const input = ImageInput.from_bytes(bytes);

      // 2. Converta. `true` significa que a compressão com perdas é permitida.
      const outcome = convert_image_to_webp_auto(input, true);

      // 3. Pegue os bytes do WebP. Leia `data` uma única vez.
      const webp = outcome.data;
      const blob = new Blob([webp], { type: "image/webp" });

      // 4. Envie o WebP só se ele for realmente menor.
      const toUpload = outcome.is_smaller ? blob : file;
      // await fetch("/upload", { method: "POST", body: toUpload });

      document.getElementById("result").textContent =
        `${outcome.original_bytes} -> ${outcome.webp_bytes} bytes ` +
        `(${outcome.mode}), cerca de ${outcome.co2_saved_grams.toFixed(4)} g de CO2e economizados`;
    } catch (e) {
      document.getElementById("result").textContent = `Falha na conversão: ${e.message ?? e}`;
    }
  });
</script>

O que aconteceu

  • init() baixa e inicia o módulo WebAssembly. Chame-o uma vez, antes de qualquer outra coisa.
  • ImageInput.from_bytes verifica qual é o formato do arquivo de imagem.
  • convert_image_to_webp_auto(input, true) faz a conversão. O segundo argumento diz se a compressão com perdas é permitida; veja Com ou sem perdas?.
  • outcome.data contém o arquivo WebP. Ele só pode ser lido uma vez; veja Memória e free().
  • outcome.is_smaller diz se a conversão realmente ajudou. Um WebP nem sempre é menor que o original, então envie o original quando o valor for false.

Mostrando uma estimativa antes

Para mostrar um tamanho aproximado antes de converter, chame preview_webp_conversion. Ela lê apenas o cabeçalho do arquivo e não codifica nada:

import { preview_webp_conversion } from "./pkg/eco_pixel.js";

const preview = preview_webp_conversion(input, true);
console.log(preview.estimated_webp_bytes, preview.confidence);

Os números vêm de regras práticas fixas por formato, então trate-os como um palpite.

Mantenha a página responsiva

A conversão é uma chamada síncrona comum, então uma imagem grande pode travar a página por um instante. Para imagens grandes, carregue o módulo e execute a conversão dentro de um Web Worker, enviando os bytes para ele com postMessage.

Usando em Rust

A crate é compilada tanto como biblioteca WebAssembly quanto como biblioteca Rust normal (rlib), então você pode chamar as mesmas funções a partir de código Rust, por exemplo em uma ferramenta de linha de comando.

Exemplo

Este exemplo usa apenas a biblioteca padrão para ler e gravar arquivos:

use eco_pixel::{convert_image_to_webp_auto, ImageInput};

fn main() {
    // Lê do disco qualquer arquivo de imagem compatível.
    let bytes: Vec<u8> = std::fs::read("photo.png").expect("não foi possível ler photo.png");

    let input = ImageInput::from_bytes(bytes).expect("imagem não reconhecida");
    let mut outcome = convert_image_to_webp_auto(&input, true).expect("falha na conversão");

    println!("{} -> {} bytes", outcome.original_bytes(), outcome.webp_bytes());
    println!("~{:.6} g de CO2e economizados (estimativa)", outcome.co2_saved_grams());

    // Guarda o WebP só se ele for realmente menor que o original.
    if outcome.is_smaller() {
        std::fs::write("photo.webp", outcome.data()).expect("não foi possível gravar photo.webp");
    } else {
        println!("O WebP não ficou menor, mantenha o arquivo original.");
    }
}

Diferenças em relação ao JavaScript

  • Os getters são métodos comuns: outcome.is_smaller() em Rust, outcome.is_smaller em JavaScript.
  • outcome.data() recebe &mut self, porque os bytes são movidos para fora. Ele pode ser chamado uma vez; as chamadas seguintes devolvem um Vec vazio.
  • Nada precisa ser liberado manualmente. O Rust descarta os valores quando saem de escopo.

Os erros funcionam melhor no navegador

As funções que podem falhar devolvem Result<_, JsError>. Um JsError só pode ser criado dentro do WebAssembly. Quando a crate roda como um programa nativo comum, uma chamada que falha, como passar bytes que não são uma imagem, entra em pânico (panic) em vez de devolver um Err. O caminho de sucesso funciona normalmente em alvos nativos. Veja Limitações.

Conceitos principais

Há três coisas para conhecer: a entrada, a prévia e o resultado.

ImageInput

ImageInput envolve os bytes brutos de um arquivo de imagem e lembra qual é o formato.

const input = ImageInput.from_bytes(new Uint8Array(await file.arrayBuffer()));
console.log(input.format);      // por exemplo "Png", "Jpeg", "Gif", "WebP"
console.log(input.byte_length); // tamanho em bytes

Se você tem a imagem como data URL (data:image/png;base64,...), use ImageInput.from_data_url(url). Quando você parte de um File, prefira from_bytes: ele pula a etapa de base64 e o acréscimo de cerca de 33% no tamanho.

Criar um ImageInput só detecta o formato. Os pixels são decodificados depois, durante a conversão. Por isso, uma imagem corrompida pode passar por esta etapa e falhar na conversão.

O mesmo ImageInput pode ser usado em várias chamadas, por exemplo uma prévia seguida de uma conversão, ou conversões com a compressão com perdas ligada e desligada.

A prévia

preview_webp_conversion(input, allowLossy) devolve uma previsão rápida sem codificar nada. Ela lê apenas o cabeçalho da imagem, então é rápida mesmo para arquivos grandes.

Ela informa as dimensões, se a origem já tem perdas, a qualidade estimada de um JPEG, se a imagem é animada e um palpite aproximado do tamanho do WebP, com uma confidence (confiança) de "low" ou "medium".

O palpite de tamanho vem de proporções fixas por formato, não de uma codificação real. Use-o para mostrar uma estimativa ou para decidir se vale a pena rodar a conversão, e confie no resultado para os números reais.

O resultado

convert_image_to_webp_auto(input, allowLossy) faz a conversão e devolve um resultado (outcome). Ele contém:

  • o arquivo WebP (data),
  • os tamanhos: original_bytes, webp_bytes e bytes_saved,
  • width e height da imagem,
  • como ela foi codificada: mode ("lossy" ou "lossless"), quality, animated e frame_count,
  • is_smaller, que diz se o WebP ficou menor que o original,
  • co2_saved_grams, o CO₂ economizado estimado.

Sempre verifique is_smaller antes de enviar o WebP. Quando for false, o arquivo original é a melhor escolha, e bytes_saved e co2_saved_grams valem 0.

Com ou sem perdas?

O WebP pode comprimir uma imagem de duas formas:

  • Sem perdas (lossless) mantém cada pixel exatamente como era. Os arquivos ficam maiores.
  • Com perdas (lossy) descarta alguns detalhes que o olho mal percebe. Os arquivos ficam bem menores, o que combina com fotografias.

O argumento allowLossy de convert_image_to_webp_auto é uma permissão para usar compressão com perdas, não uma ordem. Com false, o resultado é sempre sem perdas. Com true, a biblioteca decide com base na origem:

OrigemallowLossy = falseallowLossy = true
JPEGsem perdascom perdas, com qualidade estimada a partir do próprio JPEG (mantida entre 60 e 90)
WebP com perdassem perdascom perdas, qualidade 80
PNG, BMP, TIFF, WebP sem perdassem perdasprimeiro sem perdas; se o resultado tiver no máximo 70% do tamanho original, ele é mantido; caso contrário, uma versão com perdas (qualidade 80) também é testada e vence a menor das duas
GIFWebP animado com perdas (qualidade 75)igual; a opção não tem efeito

O que devo passar?

  • Fotos e JPEGs: passe true. Um WebP sem perdas feito a partir de um JPEG costuma ser bem maior que o JPEG, então o modo sem perdas anula o objetivo.
  • Capturas de tela, logotipos e gráficos (PNG): true continua sendo uma boa opção. A biblioteca tenta primeiro o modo sem perdas e só passa para o modo com perdas quando o primeiro não reduz o arquivo o bastante.
  • Qualquer coisa que precise ficar idêntica pixel a pixel: passe false.

Converter um JPEG para WebP com perdas comprime pela segunda vez uma imagem que já tinha perdas, o que pode acrescentar pequenos artefatos. É por isso que a qualidade é estimada a partir do JPEG e mantida dentro de uma faixa razoável.

As propriedades mode e quality do resultado mostram o que foi realmente usado.

GIF e animação

GIFs animados são convertidos em arquivos WebP animados, que os principais navegadores atuais conseguem exibir.

const input = ImageInput.from_bytes(gifBytes);
const outcome = convert_image_to_webp_auto(input, true);

console.log(outcome.animated);    // true
console.log(outcome.frame_count); // número de quadros

Como funciona

  • O WebP é sempre com perdas, com qualidade fixa de 75. A opção allowLossy não tem efeito sobre GIFs.
  • Os quadros são desenhados em uma única tela do tamanho do GIF, então quadros que só atualizam parte da imagem, e pixels transparentes, são tratados.
  • O GIF guarda o atraso de cada quadro em centésimos de segundo. Um atraso 0 é tratado como 100 ms, porque levá-lo ao pé da letra faria a animação rodar o mais rápido possível.
  • O resultado informa quality como 0 para GIFs, porque a qualidade é um valor interno fixo, e não algo estimado a partir do arquivo.
  • A prévia informa animated como true para todo GIF, inclusive um GIF com um único quadro.

Confira seus próprios GIFs

O suporte a GIF é básico. Sempre compare o resultado com o original em alguns GIFs seus antes de depender dele. Veja em Limitações o que se sabe que ainda está rudimentar.

A estimativa de CO₂

co2_saved_grams é a massa estimada de CO₂ equivalente que deixou de ser emitida porque o WebP é menor que o original.

A fórmula

co2_saved_grams = bytes_saved / 1.000.000.000   (gigabytes)
                  x 0,81                        (kWh por gigabyte transferido)
                  x 442                         (gramas de CO2e por kWh)

Isso dá cerca de 0,36 g de CO₂e para cada megabyte que não precisou ser enviado.

As duas constantes seguem o estilo do modelo Sustainable Web Design. Confira-as na versão atual desse modelo antes de citar os números em qualquer lugar.

Um exemplo

Convertendo uma foto que economiza 150 KB:

150.000 / 1.000.000.000 x 0,81 x 442  =  cerca de 0,054 g de CO2e

É muito pouco para uma única imagem. A ideia é que isso se acumula: sob as mesmas premissas, um milhão dessas imagens evitaria cerca de 54 kg de CO₂e.

O que o número inclui e o que não inclui

  • Ele conta apenas a transferência de rede que foi evitada.
  • Ele não inclui a energia que o dispositivo do visitante gasta para fazer a conversão.
  • Ele vale 0 sempre que o WebP não é menor que o original, então a biblioteca nunca declara uma economia que não obteve.
  • É uma estimativa baseada em médias, não uma medição de nenhuma rede ou rede elétrica real.

Ao mostrar o número para os usuários, indique que se trata de uma estimativa.

Memória e free()

ImageInput, a prévia e o resultado vivem na memória do WebAssembly, não no heap do JavaScript. O JavaScript guarda apenas um pequeno objeto intermediário que aponta para eles.

Preciso chamar free()?

Não. Quando o navegador oferece suporte a FinalizationRegistry, o código JavaScript de ligação gerado libera a memória automaticamente assim que o objeto intermediário é coletado pelo coletor de lixo. Chamar free() é opcional.

Ainda assim, ele é útil em dois casos:

  • Imagens grandes. free() libera a memória imediatamente, em vez de esperar o coletor de lixo resolver agir.
  • Laços de repetição. O coletor de lixo não consegue rodar no meio de código síncrono. Se você converte muitas imagens em um único laço, sem nenhum await dentro dele, a memória só é recuperada quando o laço termina, e um lote grande pode esgotar a memória. Chame free() em cada objeto, ou use await em algo dentro do laço para que a limpeza possa acontecer.
input.free();
outcome.free();

Um objeto não pode ser usado depois de free().

Leia os dados apenas uma vez

outcome.data entrega os bytes do WebP em vez de copiá-los. A primeira leitura devolve o arquivo inteiro e qualquer leitura seguinte devolve um array vazio. Leia uma única vez para uma variável:

const webp = outcome.data; // guarde isto

As outras propriedades, como webp_bytes e co2_saved_grams, continuam funcionando depois que data foi lido.

Da mesma forma, input.bytes devolve uma cópia dos bytes originais a cada leitura, o que é lento para arquivos grandes. Raramente você precisa dele, já que você já tem os bytes que passou.

Problemas comuns

O módulo não carrega. Sirva a página por HTTP em vez de abri-la com file:// e garanta que os arquivos .wasm sejam enviados como application/wasm. Veja Compilando o pacote.

Um erro sobre algo indefinido logo no início. Garanta que você use await init() uma vez antes de chamar qualquer outra coisa.

RuntimeError: unreachable. É assim que um pânico (panic) do Rust aparece em WebAssembly. A biblioteca instala um gancho de pânico, então a mensagem real do pânico é exibida no console do navegador: abra as ferramentas de desenvolvedor e leia o primeiro erro. Depois de um pânico, o módulo WebAssembly pode ficar em um estado inconsistente; por isso, recarregue a página antes de tentar de novo e evite chamar free() em objetos que estavam em uso quando isso aconteceu.

outcome.data está vazio. Ele já foi lido. data só pode ser lido uma vez; guarde o primeiro resultado em uma variável. Veja Memória e free().

O WebP ficou maior que o original. Isso acontece, principalmente com WebP sem perdas feito a partir de um JPEG. Verifique outcome.is_smaller e envie o arquivo original quando for false. Passar true em allowLossy costuma evitar o problema em fotos.

A página trava durante a conversão. A conversão é síncrona. Execute-a em um Web Worker para imagens grandes; veja o Início rápido.

A prévia ficou bem longe do tamanho real. Isso é esperado às vezes. A prévia usa proporções fixas por formato e nunca codifica nada. Use o resultado para os números reais.

Limitações

O que é preciso saber antes de confiar no EcoPixel.

O valor de CO₂ é uma estimativa

Ele é construído a partir de médias e conta apenas a transferência de rede evitada. Ignora a energia gasta no dispositivo do visitante. Veja A estimativa de CO₂.

Um WebP nem sempre é menor

Um WebP sem perdas feito a partir de um JPEG costuma ser bem maior que o JPEG, e algumas imagens simplesmente não diminuem. Sempre verifique is_smaller. Quanto o WebP com perdas economiza em relação ao JPEG depende da imagem e de quão bem o JPEG foi comprimido desde o início; não presuma uma porcentagem fixa. Meça com as suas próprias imagens.

A prévia é um palpite

preview_webp_conversion usa regras práticas fixas por formato. Serve apenas como uma indicação aproximada.

As configurações de perdas são fixas

Você escolhe se a compressão com perdas é permitida, mas não a qualidade. A biblioteca a define: estimada a partir do arquivo nos JPEGs (mantida entre 60 e 90), 80 para as demais conversões com perdas e 75 para GIFs.

O suporte a GIF é básico

  • Os quadros são desenhados em uma tela, mas a configuração de “método de descarte” (disposal method) do GIF, que diz o que fazer com a área de um quadro antes do quadro seguinte, não é aplicada com precisão na ordem que a especificação do GIF descreve. Alguns GIFs que dependem dela podem não ficar idênticos.
  • O último quadro da animação é exibido pelo mesmo tempo que o primeiro, em vez de usar o seu próprio atraso.

Teste com os seus próprios GIFs antes de depender do resultado.

Erros em alvos Rust nativos

Os erros são valores JsError, que só podem ser criados dentro do WebAssembly. Em um alvo nativo, uma chamada que falha entra em pânico (panic) em vez de devolver um Err. Use a crate em Rust principalmente para o caminho de sucesso, ou valide a entrada antes de chamá-la. Veja Usando em Rust.

Uma thread, sem redimensionamento

A conversão roda em uma única thread e bloqueia até terminar. A biblioteca apenas converte formatos; ela não redimensiona nem recorta imagens, então reduza você mesmo as imagens muito grandes se não precisar da resolução completa.
