EcoPixel

EcoPixel

EcoPixel converts images to WebP on the visitor’s device and tells you how much CO₂ the smaller upload avoided.

It is written in Rust and compiled to WebAssembly, so a website can call it from JavaScript. It can also be used as an ordinary Rust crate.

Why convert in the browser?

Normally the browser uploads the original PNG or JPEG and the server converts it, if anything converts it at all. If the browser converts the image first, a smaller file travels over the network and the server has less to do. The amount of data that did not have to travel is what the CO₂ figure is based on.

The figure is an estimate, not a measurement. See The CO₂ estimate for exactly what it counts.

What it does

  • Reads PNG, JPEG, GIF, BMP, TIFF and WebP files, given as bytes or as a data URL.
  • Converts them to WebP: lossless, lossy, or picked automatically.
  • Turns animated GIFs into animated WebP.
  • Reports the original size, the new size, the bytes saved and the estimated CO₂ saved.
  • Runs entirely on the visitor’s device. Nothing is uploaded by the library.

The flow in four steps

  1. Wrap the file with ImageInput. This detects the format.
  2. Optionally preview the conversion. It gives a quick size estimate without encoding.
  3. Convert the image. You get the WebP bytes and the statistics.
  4. Use the result. Upload the WebP, or the original file if the WebP turned out not to be smaller.

Continue with Building the package, or jump to the Quick start if you already have the built package.

Building the package

EcoPixel is compiled to WebAssembly with wasm-pack, which also generates the JavaScript wrapper and the TypeScript type definitions.

Prerequisites

You need a Rust toolchain, the WebAssembly target and wasm-pack:

rustup target add wasm32-unknown-unknown
cargo install wasm-pack

Build

Run this in the crate’s folder:

wasm-pack build --target web --release

The result is a pkg/ folder containing:

FileWhat it is
eco_pixel_bg.wasmThe compiled library
eco_pixel.jsJavaScript glue code; this is what you import
eco_pixel.d.tsTypeScript types, including the documentation comments
package.jsonPackage metadata, so the folder can be published or installed

Rebuild after every change to the Rust code, and hard-refresh the page (Ctrl+F5) so the browser doesn’t use a cached copy.

Choosing a target

--targetUse it forNotes
webPlain browsers, Vite, Web WorkersCall await init() once before using anything
bundlerWebpack, and bundlers with WebAssembly supportNo init() call; needs a bundler that can import .wasm files
nodejsNode.js scriptsNot useful for converting images in the visitor’s browser

This book uses web.

Serving the files

Browsers refuse to load WebAssembly from a page opened with file://. Serve the folder over HTTP with any static file server. For example:

python -m http.server 8080

Then open http://localhost:8080/. The server must send .wasm files with the content type application/wasm. Most static servers do this, and it is the first thing to check if the module fails to load.

Quick start (JavaScript)

This page is a complete example: pick an image, convert it to WebP, and show how much was saved. It assumes you have built the package (see Building the package) and that the pkg/ folder sits next to your HTML file.

<input id="file" type="file" accept="image/*">
<p id="result"></p>

<script type="module">
  import init, { ImageInput, convert_image_to_webp_auto } from "./pkg/eco_pixel.js";

  await init(); // load the WebAssembly module once

  document.getElementById("file").addEventListener("change", async (event) => {
    const file = event.target.files[0];
    if (!file) return;

    try {
      // 1. Wrap the file bytes.
      const bytes = new Uint8Array(await file.arrayBuffer());
      const input = ImageInput.from_bytes(bytes);

      // 2. Convert. `true` means lossy compression is allowed.
      const outcome = convert_image_to_webp_auto(input, true);

      // 3. Take the WebP bytes. Read `data` once.
      const webp = outcome.data;
      const blob = new Blob([webp], { type: "image/webp" });

      // 4. Upload the WebP only if it is really smaller.
      const toUpload = outcome.is_smaller ? blob : file;
      // await fetch("/upload", { method: "POST", body: toUpload });

      document.getElementById("result").textContent =
        `${outcome.original_bytes} -> ${outcome.webp_bytes} bytes ` +
        `(${outcome.mode}), about ${outcome.co2_saved_grams.toFixed(4)} g CO2e saved`;
    } catch (e) {
      document.getElementById("result").textContent = `Conversion failed: ${e.message ?? e}`;
    }
  });
</script>

What happened

  • init() downloads and starts the WebAssembly module. Call it once, before anything else.
  • ImageInput.from_bytes checks which image format the file is.
  • convert_image_to_webp_auto(input, true) does the conversion. The second argument says whether lossy compression is allowed; see Lossy or lossless?.
  • outcome.data holds the WebP file. It can be read only once; see Memory and free().
  • outcome.is_smaller tells you whether converting actually helped. A WebP is not always smaller than the original, so upload the original when it is false.

Showing an estimate first

To show a rough size before converting, call preview_webp_conversion. It reads only the file header and does not encode anything:

import { preview_webp_conversion } from "./pkg/eco_pixel.js";

const preview = preview_webp_conversion(input, true);
console.log(preview.estimated_webp_bytes, preview.confidence);

The numbers come from fixed rules of thumb per format, so treat them as a guess.

Keep the page responsive

Conversion is a normal synchronous call, so a large image can freeze the page for a moment. For big images, load the module and run the conversion inside a Web Worker, and pass the bytes to it with postMessage.

Using it from Rust

The crate is built as both a WebAssembly library and a normal Rust library (rlib), so you can call the same functions from Rust code, for example in a command-line tool.

Example

This example uses only the standard library to read and write files:

use eco_pixel::{convert_image_to_webp_auto, ImageInput};

fn main() {
    // Read any supported image file from disk.
    let bytes: Vec<u8> = std::fs::read("photo.png").expect("could not read photo.png");

    let input = ImageInput::from_bytes(bytes).expect("not a recognised image");
    let mut outcome = convert_image_to_webp_auto(&input, true).expect("conversion failed");

    println!("{} -> {} bytes", outcome.original_bytes(), outcome.webp_bytes());
    println!("~{:.6} g CO2e saved (estimate)", outcome.co2_saved_grams());

    // Keep the WebP only when it is actually smaller than the original.
    if outcome.is_smaller() {
        std::fs::write("photo.webp", outcome.data()).expect("could not write photo.webp");
    } else {
        println!("The WebP is not smaller, keep the original file.");
    }
}

Differences from JavaScript

  • Getters are plain methods: outcome.is_smaller() in Rust, outcome.is_smaller in JavaScript.
  • outcome.data() takes &mut self, because the bytes are moved out. It can be called once; later calls return an empty Vec.
  • Nothing needs to be freed. Rust drops the values when they go out of scope.

Errors work best in the browser

Functions that can fail return Result<_, JsError>. A JsError can only be created inside WebAssembly. When the crate runs as a normal native program, a failing call, such as passing bytes that are not an image, panics instead of returning an Err. The success path works normally on native targets. See Limitations.

Core concepts

There are three things to know: the input, the preview and the outcome.

ImageInput

ImageInput wraps the raw bytes of an image file and remembers which format they are.

const input = ImageInput.from_bytes(new Uint8Array(await file.arrayBuffer()));
console.log(input.format);      // for example "Png", "Jpeg", "Gif", "WebP"
console.log(input.byte_length); // size in bytes

If you have the image as a data URL (data:image/png;base64,...), use ImageInput.from_data_url(url) instead. When you start from a File, prefer from_bytes: it skips the base64 step and its roughly 33% size overhead.

Creating an ImageInput only detects the format. The pixels are decoded later, during conversion. A corrupt image can therefore pass this step and fail at conversion.

The same ImageInput can be used for several calls, for example a preview followed by a conversion, or conversions with lossy on and off.

The preview

preview_webp_conversion(input, allowLossy) returns a quick forecast without encoding anything. It reads only the header of the image, so it is fast even for large files.

It tells you the dimensions, whether the source is already lossy, the estimated quality of a JPEG, whether the image is animated, and a rough guess of the WebP size, with a confidence of "low" or "medium".

The size guess comes from fixed ratios per format, not from real encoding. Use it to show an estimate or to decide whether a conversion is worth running, and rely on the outcome for real numbers.

The outcome

convert_image_to_webp_auto(input, allowLossy) does the conversion and returns an outcome. It holds:

  • the WebP file (data),
  • sizes: original_bytes, webp_bytes and bytes_saved,
  • the image width and height,
  • how it was encoded: mode ("lossy" or "lossless"), quality, animated and frame_count,
  • is_smaller, which tells you whether the WebP beat the original,
  • co2_saved_grams, the estimated CO₂ saved.

Always check is_smaller before uploading the WebP. When it is false, the original file is the better choice, and bytes_saved and co2_saved_grams are 0.

Lossy or lossless?

WebP can compress an image in two ways:

  • Lossless keeps every pixel exactly as it was. Files are bigger.
  • Lossy throws away some detail the eye barely notices. Files are much smaller, which suits photographs.

The allowLossy argument of convert_image_to_webp_auto is permission to use lossy compression, not an order. With false the output is always lossless. With true, the library decides based on the source:

SourceallowLossy = falseallowLossy = true
JPEGlosslesslossy, with a quality estimated from the JPEG itself (kept between 60 and 90)
Lossy WebPlosslesslossy, quality 80
PNG, BMP, TIFF, lossless WebPlosslesslossless first; if that is at most 70% of the original size it is kept, otherwise a lossy version (quality 80) is also tried and the smaller of the two wins
GIFanimated lossy WebP (quality 75)same; the flag has no effect

Which should I pass?

  • Photos and JPEGs: pass true. A lossless WebP made from a JPEG is usually much bigger than the JPEG, so lossless defeats the purpose.
  • Screenshots, logos and graphics (PNG): true is still fine. The library tries lossless first and only switches to lossy when lossless doesn’t shrink the file enough.
  • Anything that must stay pixel-exact: pass false.

Converting a JPEG to lossy WebP compresses an already-lossy image a second time, which can add small extra artifacts. This is why the quality is estimated from the JPEG and kept within a sensible range.

The mode and quality properties of the outcome tell you what was actually used.

GIF and animation

Animated GIFs are converted into animated WebP files, which current major browsers can display.

const input = ImageInput.from_bytes(gifBytes);
const outcome = convert_image_to_webp_auto(input, true);

console.log(outcome.animated);    // true
console.log(outcome.frame_count); // number of frames

How it works

  • The WebP is always lossy, at a fixed quality of 75. The allowLossy flag has no effect on GIFs.
  • Frames are drawn onto one canvas the size of the GIF, so frames that only update part of the picture, and transparent pixels, are handled.
  • GIF stores frame delays in hundredths of a second. A delay of 0 is treated as 100 ms, because taking it literally would make the animation play as fast as possible.
  • The outcome reports quality as 0 for GIFs, because the quality is a fixed internal value, not something estimated from the file.
  • The preview reports animated as true for every GIF, including a GIF with one frame.

Check your own GIFs

GIF support is basic. Always compare the result with the original on a few of your own GIFs before relying on it. See Limitations for what is known to be rough.

The CO₂ estimate

co2_saved_grams is the estimated mass of CO₂-equivalent that was not emitted because the WebP is smaller than the original.

The formula

co2_saved_grams = bytes_saved / 1,000,000,000   (gigabytes)
                  x 0.81                        (kWh per gigabyte transferred)
                  x 442                         (grams of CO2e per kWh)

That is roughly 0.36 g of CO₂e for every megabyte that did not have to be uploaded.

The two constants follow the style of the Sustainable Web Design model. Check them against the current version of that model before quoting the numbers anywhere.

An example

Converting a photo that saves 150 KB:

150,000 / 1,000,000,000 x 0.81 x 442  =  about 0.054 g CO2e

That is tiny for one image. The idea is that it adds up: under the same assumptions, a million such images would avoid about 54 kg of CO₂e.

What the number does and does not include

  • It counts only the network transfer that was avoided.
  • It does not include the energy the visitor’s device spends doing the conversion.
  • It is 0 whenever the WebP is not smaller than the original, so the library never claims savings it did not achieve.
  • It is an estimate based on averages, not a measurement of any real network or power grid.

When you show the number to users, label it as an estimate.

Memory and free()

ImageInput, the preview and the outcome live in WebAssembly memory, not in the JavaScript heap. JavaScript only holds a small wrapper object that points to them.

Do I have to call free()?

No. When the browser supports FinalizationRegistry, the generated JavaScript glue releases the memory automatically once the wrapper object is garbage collected. Calling free() is optional.

It is still useful in two cases:

  • Large images. free() releases the memory immediately instead of whenever the garbage collector gets around to it.
  • Loops. The garbage collector cannot run in the middle of synchronous code. If you convert many images in one loop with no await inside it, the memory is not reclaimed until the loop ends, and a big batch can run out of memory. Call free() on each object, or await something inside the loop so cleanup can happen.
input.free();
outcome.free();

An object cannot be used after free().

Reading the data only once

outcome.data hands the WebP bytes over instead of copying them. The first read returns the whole file and any later read returns an empty array. Read it once into a variable:

const webp = outcome.data; // keep this

The other properties, such as webp_bytes and co2_saved_grams, keep working after data has been read.

Similarly, input.bytes returns a copy of the original bytes every time it is read, which is slow for large files. You rarely need it, since you already have the bytes you passed in.

Common problems

The module fails to load. Serve the page over HTTP instead of opening it with file://, and make sure .wasm files are sent as application/wasm. See Building the package.

An error about something being undefined right at the start. Make sure you await init() once before calling anything else.

RuntimeError: unreachable. This is how a Rust panic looks in WebAssembly. The library installs a panic hook, so the actual panic message is printed in the browser console: open the developer tools and read the first error. After a panic the WebAssembly module can be left in an inconsistent state, so reload the page before trying again, and avoid calling free() on objects that were in use when it happened.

outcome.data is empty. It was already read. data can be read only once; keep the first result in a variable. See Memory and free().

The WebP is bigger than the original. This happens, especially for lossless WebP made from a JPEG. Check outcome.is_smaller and upload the original file when it is false. Passing true for allowLossy usually avoids it for photos.

The page freezes during conversion. Conversion is synchronous. Run it in a Web Worker for large images; see the Quick start.

The preview was far from the real size. That is expected sometimes. The preview uses fixed ratios per format and never encodes anything. Use the outcome for real numbers.

Limitations

Things to know before you rely on EcoPixel.

The CO₂ number is an estimate

It is built from averages and counts only the avoided network transfer. It ignores the energy spent on the visitor’s device. See The CO₂ estimate.

A WebP is not always smaller

Lossless WebP made from a JPEG is usually much bigger than the JPEG, and some images simply do not shrink. Always check is_smaller. How much lossy WebP saves compared with JPEG depends on the image and on how well the JPEG was compressed in the first place; do not assume a fixed percentage. Measure with your own images.

The preview is a guess

preview_webp_conversion uses fixed rules of thumb per format. It is meant for a rough indication only.

Lossy settings are fixed

You choose whether lossy is allowed, but not the quality. The library picks it: estimated from the file for JPEGs (kept between 60 and 90), 80 for other lossy conversions and 75 for GIFs.

GIF support is basic

  • Frames are drawn onto a canvas, but the GIF “disposal method” setting, which says what to do with a frame’s area before the next frame, is not applied precisely in the order the GIF specification describes. Some GIFs that rely on it may not look identical.
  • The last frame of the animation is shown for as long as the first frame, instead of using its own delay.

Test with your own GIFs before depending on the result.

Errors on native Rust targets

Errors are JsError values, which can only be created inside WebAssembly. On a native target, a failing call panics instead of returning an Err. Use the crate from Rust mainly for the success path, or validate input before calling it. See Using it from Rust.

One thread, no resizing

Conversion runs on one thread and blocks until it finishes. The library only converts formats; it does not resize or crop images, so downscale very large images yourself if you do not need the full resolution.
